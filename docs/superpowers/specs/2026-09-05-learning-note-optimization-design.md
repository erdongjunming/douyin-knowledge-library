# 抖音完整教学笔记整理优化设计

**日期：** 2026-09-05  
**状态：** 已确认方向，待用户审阅设计文档  
**适用项目：** Douyin Knowledge Library

## 1. 背景与问题

当前笔记链路已经具备字幕/ASR 事实主干、evidence atom、逐段时间线、主题合成、覆盖审查和一次修复。但一次性合成整篇笔记时，模型仍可能把内容压缩成几句漂亮的概括，导致：

- 核心观点与支撑它的例子、结果、限定条件分离；
- 有序步骤被概括成一个动作；
- 数字、专名、风险和推广内容在主题正文中消失，只剩时间线可查；
- 审查只证明“出现过”，没有充分证明“讲清楚”；
- 长视频的细节互相争抢输出预算。

本设计把主交付物明确为“完整教学版学习笔记”：去掉无信息的口头冗余，但保留所有有效观点、依据、例子、结果、步骤、条件、数字、风险和原话证据。

## 2. 目标

1. 让读者不回看视频，也能按主题理解视频的论点、方法、例子和边界。
2. 让每个核心观点都能追溯到原文片段和时间点。
3. 让例子、结果和限定条件回到对应主题，而不是只出现在附录时间线。
4. 在证据不足或依赖画面时明确降级，不用模型常识补写视频没有提供的内容。
5. 让历史笔记可以复用已有字幕、ASR 和原始资产，只重做语义笔记。
6. 保持本地 Ollama 为主链路，豆包不进入事实主链，也不绕过验证码或导出登录凭据。

## 3. 非目标

- 不在本设计中重新设计抖音抓取、字幕提取或 Qwen3-ASR。
- 不把抖音问 AI、豆包快读或视觉假设写成完整字幕或视频原话。
- 不以固定字数强行扩写缺乏证据的短视频。
- 不覆盖账号分析、评论洞察和话题研究的独立输出模板。
- 不通过覆盖旧文件来掩盖新笔记生成失败。

## 4. 总体流程

```text
NoteInput（字幕/ASR/元数据）
  -> Evidence extraction（原子证据账本）
  -> Teaching outline（教学大纲和章节证据分配）
  -> Section synthesis（按章节生成）
  -> Coverage + depth review（完整度与深度审查）
  -> Bounded repair（一次限定修复）
  -> Deterministic render（固定结构 Markdown、时间线和证据图）
```

### 4.1 证据提取

继续使用现有分段、atom ID、segment disposition 和跨批次关系。提取阶段必须保留：

- claim、reason、definition、step、example、counterexample、condition、warning、number、quote、recommendation 和 promotion；
- 原文 excerpt、segment index、时间点、关系、步骤序号；
- ASR 不确定词；
- 每个源 segment 恰好一个 disposition。

这一阶段不负责写漂亮的摘要，只负责建立后续章节可以复用的完整证据账本。

### 4.2 教学大纲

在全局 evidence atoms 合并后，新增一个教学大纲阶段。大纲为每个章节分配相关 atom，并标记该章节需要检查的证据类型。

固定章节顺序为：

1. 一句话总览
2. 核心观点
3. 方法与步骤
4. 例子与结果
5. 前提、边界与风险
6. 可执行行动
7. 完整逐段时间线
8. 证据与 ASR 局限

大纲必须保留 atom 到章节的映射。一个 atom 可以被多个章节引用，但同一事实在正文中应避免无意义重复。

### 4.3 分章节生成

每章以独立证据清单和独立输出预算生成。逻辑上每章都必须满足以下约束：

- 核心观点必须带 atom ID 和时间点；
- 例子必须带结果，不能只写“有一个案例”；
- 步骤必须保留顺序和步骤之间的条件关系；
- 条件、例外、风险和警告必须与适用的观点或步骤相邻；
- 数字、专名、引语和不确定词不得被泛化；
- 视频没有提供的内容写为“视频未提供”，不得用常识补齐；
- 生成理解和作者原话必须分开标识。

章节生成可以在同一次本地 Ollama 任务中按安全上下文预算分组，但数据契约必须按章节独立，便于重试单章而不重跑整条视频。

## 5. 数据契约

### 5.1 TeachingOutline

至少包含：

- `sections`：固定章节 ID、标题和顺序；
- `atom_ids`：该章节负责覆盖的证据 atom；
- `required_evidence_types`：步骤、例子、条件、风险等要求；
- `missing_evidence_policy`：无对应证据时输出“视频未提供”；
- `timestamps`：章节涉及的源时间范围。

### 5.2 SectionDraft

至少包含：

- `section_id`、`title`、`content`；
- `claims`：每条主张的正文、`atom_ids` 和时间点；
- `examples`、`results`、`conditions`、`risks`、`actions`；
- `unprovided_items`：视频明确没有提供的内容；
- `included_atom_ids`。

所有引用的 atom 必须存在于全局证据命名空间。章节之间合并时只允许确定性去重，不允许重新解释或删除唯一证据。

### 5.3 DepthReview

在现有 CoverageReview 之外，记录：

- 被抽象化的 atom；
- 缺少结果的例子；
- 缺少适用条件的步骤或观点；
- 被合并导致顺序丢失的步骤；
- 丢失的数字、专名、警告、推广或 ASR 不确定标记；
- 没有 atom 支撑的正文主张；
- 需要修复的章节 ID。

只有覆盖审查和深度审查都通过，且输入证据充分，才允许标记为 `semantic_complete`。

## 6. 完整度与降级规则

### 6.1 完整教学版通过条件

- 每个源 segment 都有 disposition；
- 每个纳入 atom 同时能在主题章节和时间线中找到；
- 核心观点均有来源和时间点；
- 步骤、例子/结果、条件/风险的覆盖状态通过；
- 没有 unsupported claims；
- 深度审查没有未修复的压缩项；
- 没有超出输入证据的视觉或事实推断。

### 6.2 证据不足

若 ASR/字幕稀疏，或内容依赖画面文字、镜头和操作：

- 仍可生成一份可读的降级笔记；
- 在正文和“证据与 ASR 局限”中明确标出缺口；
- 不把缺口补成作者观点或视频事实；
- 以 `quality_gate=failed` 或现有状态机等价的非完成状态发布；
- 质量状态不得为 `semantic_complete`，继续保持可升级状态；
- 豆包、抖音问 AI、关键帧或 OCR 若未实际取得，不得写成已核实证据。

### 6.3 Provider 或发布失败

Provider 调用、章节合并、深度修复或原子发布失败时：

- 不把任务计为成功；
- 保留旧的可读笔记和原始资产；
- 写入失败 audit、阶段和错误原因；
- 历史升级任务保持可重试。

## 7. Markdown 渲染

`learning_note.md` 以主题化教学正文为主，完整时间线为证据附录。每个主题项应尽量使用以下顺序：

```text
观点/步骤
  -> 原文依据与时间点
  -> 解释
  -> 例子与结果
  -> 适用条件/限制
  -> 风险或行动
```

章节没有对应证据时渲染固定的“视频未提供这一类信息”，而不是空白或泛化句。`evidence_map.json`、`coverage_report.json`、`note_budget.json` 和 `note_score.json` 继续作为机器可审计资产。

## 8. 预算、性能与复用

- 输出预算由转写长度、segment 数量、atom 数量和章节证据类型决定，不使用一刀切字数。
- 长视频优先按章节和上下文安全边界分组，避免单次 Ollama 输出挤压其他章节。
- 提取结果、大纲和已通过章节应可缓存；单章失败只重试该章和必要的最终审查。
- 默认本地 Ollama 顺序处理需要共享 GPU 的章节，避免并发抢占；非模型的合并和渲染保持确定性。
- 历史升级复用已有 `transcript.txt`、`segments.json`、元数据和资产清单，不重复下载或 ASR。

## 9. 质量状态与历史升级

`semantic_complete` 只表示“证据覆盖、深度审查和输入充分性均通过”。降级笔记可以被发布和阅读，但不能被当作完成品；历史升级候选继续包括 `legacy`、`fallback` 和 `unknown`。

新 bundle 通过完整校验并原子发布后才替换旧 bundle。旧 bundle 在任何 provider、审查或发布失败时保持不变。

## 10. 测试与验收标准

### 10.1 单元测试

- TeachingOutline、SectionDraft、DepthReview 的严格 schema 校验；
- 每条主张缺少 atom、时间点或必要证据时失败；
- 步骤顺序、例子结果、条件和风险的深度审查；
- 数字、专名、推广和 ASR 不确定标记的保留；
- “视频未提供”与视觉依赖警告不能被误判为事实。

### 10.2 Pipeline 测试

使用包含“三步方法 + 案例结果 + 限定条件 + 风险 + 推广”的固定 fixture，验证：

- 五个主要教学章节都能拿到对应证据；
- 例子和条件出现在主题正文，不只出现在时间线；
- 缺失一项时只修复对应章节；
- 修复仍失败时生成降级状态，不发布为 `semantic_complete`；
- 长输入分批后不丢失 atom、顺序和跨批关系。

### 10.3 集成与历史升级测试

- 新笔记只在语义完整 bundle 发布成功后计为成功；
- 历史 `legacy/fallback/unknown` 可按上限升级；
- 升级失败、取消或 false-success 不被计为完成；
- 旧笔记和原始 transcript 在失败时保持不变；
- 进度接口区分普通笔记和语义升级进度。

### 10.4 用户验收

选取此前被认为过于简洁的“姜学长”视频作为回归样本，人工检查：

- 是否能在主题正文看到完整步骤；
- 每个案例是否包含做法和结果；
- 限定条件、例外和风险是否紧邻相关观点；
- 是否明确区分视频原话、ASR 不确定和生成理解；
- 没有画面证据时是否明确降级而不是编造。

## 11. 取舍与风险

- 分章节生成会增加本地 Ollama 调用次数和等待时间，但可显著降低长内容互相压缩的风险。
- 更严格的深度审查会让部分短视频进入降级状态；这是证据优先的预期结果，不应通过放宽门槛解决。
- 主题化正文会重排视频顺序，因此完整时间线和 evidence map 必须继续保留，避免失去原始上下文。
- 章节级缓存和修复会增加中间状态，但能减少历史视频重复 ASR 和整篇重做。

## 12. 实施边界

本设计获审阅后，下一步只制定实现计划。实现计划应优先覆盖数据契约和失败测试，再实现章节调度、深度审查、渲染和历史升级回归；不在本阶段加入新的外部 provider 或自动绕过人机识别的流程。
